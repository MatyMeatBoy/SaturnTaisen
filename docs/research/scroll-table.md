# Scroll-picture table (TP2)

Patches 0098, 0119, 0122, 0124 and 0128 each connected one scroll picture with its own constants and code. Patch 0135 replaces them with one table (`port/scroll_picture_rows.h`, generated by `tools/gen_scroll_pictures.py`, mirrored in `config/hd-scroll-pictures.json`) and one draw path.

## The common rule

The Saturn shows a 288×144 window (at 16,8 of the 320×224 frame) of a larger NBG2 picture. The window slides along one axis only, and the PC art is the same picture at exactly 2×:

- Horizontal pictures are N×144 (N = 432..512) with PC art 2N×320. For native offset x the PC crop is (2x, 16, 576, 288); 16 is the centred cross margin (320 − 288) / 2.
- Vertical pictures are 288×M (M = 208 or 296) with PC art 576×2M. The crop is (0, 2y, 576, 288); the centred cross margin is (576 − 576) / 2 = 0.

So a row is (picture, axis, native size, PC size) plus pins: Saturn file size and FNV, the PC file size and FNV, the VDP2 palette key and the first-uniquely-named-cell key of layer 4. The offset is never read from registers: the runtime still finds it by comparing the presented NBG2 pixels with the pinned native picture (exact RGB, unique offset), so the PC crop is only drawn when the native crop is proven. `ScrollPcCrop` and `ScrollRowValid` encode the rule and `tests/test_scroll_pictures.cpp` checks it for every row.

The generator selects candidates from the wide and tall picture inventory, so changing coverage status does not change which candidates it examines. It leaves design exclusions and the separate BG1306, BG2238 and BG2260 still-viewport paths outside this table.

The generator derives each row offline from the Saturn BIN (name table header gives the size; palette and cell keys reproduce the live fingerprints) and the PC SPR (subimage 0 size). It refuses a picture unless PC art is 2× on the scroll axis with an even centred margin on the other, and unless an 8-pixel-stride sweep of every native window correlates with the matching PC crop at 0.90 or better (grey signature, tools/match_hd_all.py). The keys it derives for BG1207, BG1285, BG2248, BG2295 and BG2533 equal the constants that were recorded from live runs.

## Rows

Existing behaviour is kept: BG2533 (edge ramp, identified by palette alone), BG1207 (opaque NBG0 actress preserved), BG1285 (plain), BG2248 and BG2295 (vertical).

New rows, by data only (no in-game check): horizontal BG1282, BG2130, BG2515; vertical BG2176. The Chapter 10 forest set BG2207, BG2265-BG2269 (patch 0132) is also rows of this table, so each picture is drawn once. The forest PC files are colour variants of one picture; each is paired by name and pinned by its own file hash, and the derived keys equal the ones in the earlier private forest study.

Not added (the generator prints the reason, kept under `skipped` in the JSON):

- BG1257, BG1280, BG2077, BG2093, BG2172: PC width/height is not 2× the native picture (needs a per-picture crop).
- BG1283, BG1310, BG2247, BG2290, BG2518: sizes fit but the PC art does not follow the native picture at the default 2x crop (correlation 0.20..0.88), so the crop needs a measured offset. BG1283, BG1310, BG2518 and BG2290 now have calibrated rows (below); BG2247 stays native.
- BG2338 has no variant-B table. The separate BG2238 still uses its own path from patch 0123. The seven BBG pictures are 320×224 battle frames, not a 288×144 window (TP2b).

## Evidence and limits

- The rebased implementation matched 1,500 opening hashes, 205 BG2248 and 60 BG2251 hashes, and 60 hashes each for BG1207, BG1285 and BG2533. The five scene controls matched all 18 sampled 2560×1440 captures. The BG2533 missing-donor control verified its active edge ramp.
- Opening film replay (SATRECOMP_SKIP_CHOOSER, strict native, 6201 guest frames) with the new runtime matches the previous `frames.hash` byte for byte, with zero interpreted blocks.
- C++ tests: `tests/test_bg2533_pan.cpp`, `test_bg2248_pan.cpp`, `test_bg1207_pan.cpp` (unchanged) and `test_scroll_pictures.cpp` (rule, unique keys, existing crops, lookup, 456- and 512-wide matcher). Compile each with `clang++ -std=gnu++20 -I<satrecomp>/port`.
- The new rows are not seen in a replay. They draw only when the live layer keys and the exact native window match, and otherwise leave the native composition. Appearance and package inclusion stay open.

## BG2290: minimum offset and end clamp (TP2a12, patch 0188)

BG2290 is 432x144 with a 864x320 PC picture. The PC art does not start where the Saturn picture does: a single crop `start = -68 + 2.150 * offset`, 620 PC pixels wide and the full 320-pixel height, scores 0.9897 to 0.9993 (mean 0.9922) against every integer native offset from 32 to 144 (113 positions, generator signature). Below offset 32 the crop would begin left of the PC picture (start -68 at offset 0, 0 at offset 31), and the best crop that stays inside the PC picture (start 0) scores 0.70 at offset 0, 0.82 at 16 and only reaches 0.926 at 24, where the fitted start is still negative. The offsets below 32, the x=0 hold the [live stage-wing pan](bg2290-native-pan.md) shows for 4,000 to 4,250 frames and the x=18 sample, therefore stay native. The PC crop enters gradually over offsets 33–47 and reaches full opacity at x=48.

Three optional controls were added to the calibrated fit (`ScrollFit` in `port/scroll_pictures.h`, written by `tools/gen_scroll_pictures.py` from `FIT_OPTIONS`):

- `min_offset`: native offsets below it are not drawn from the PC art (the native picture stays). `ScrollOffsetSupported` is checked by the frontend after the exact native viewport match, so the guard only removes draws.
- `clamp_end`: the crop start is limited to `pcLength - length`, so the end of the crop never runs past the PC picture. BG2290 ends at 242 + 620 = 862 of 864, so the clamp does not move any crop today; it is the safety the review asked for.

- The 16-offset fade keeps x=32 pixel-identical to Saturn and reaches full donor opacity at x=48.

`origin` is now signed (BG2290 starts at -68). Rows without options are written exactly as before (`{rate, origin, length, cross, crossLength}`) and keep `minOffset 0`, `clampEnd false`, so every other row draws the same crops. `ScrollRowValid` requires the first supported crop to start inside the PC picture and, without the clamp, the last crop to end inside it. Tests: `tests/test_scroll_pictures.cpp` (real BG2290 row plus synthetic rows with negative origin, minimum offset, clamp and out-of-range minimum) and `tests/test_gen_scroll_pictures.py` (the generator's crop function).

The natural English disc 1 stage-wing replay verifies the HD draw, opacity
ramp and native fallback at 1440p. The disc 2 row remains wired-unverified.
The [replay and seam measurements](bg2290-native-pan.md#enhanced-donor-fade)
record the draw and the native timing.

## Remaining dispositions (TP2a12)

- BG2338 (320x160, PC `BG2238.SPR` subimage 17, 0.943 whole-picture): **stays native for now, not in this table.** It shares palette `5DEDEF54BF2F059D` with the BG2238 still but has its own cell key `9E591B2DBD322D38`, a fixed-cell (not variant-B) layout and a different PC subimage and box than the BG2238 crop (8,28,544,272 of subimage 0). It is not a pan, so it would need its own still path like patch 0123 (own palette, cell hash, viewport check and crop). Nothing records where, on which layer or how long the Saturn shows it: the replays that read BG2338 do not exist (FAD 128990 was never read in the archived continuations and 1,062 native screenshots do not contain it). Wiring it blind would guess the viewport, so the first step is a replay that reaches it; the keys above are what that still path needs.
- BG1257 (456x144), BG1280 (512x144) and BG2247 (288x296) stay native. The default 2x rule fails by size (PC 1181x320, 1241x320) and a free per-window crop does not align: BG1257 scores 0.863 minimum and 0.879 mean, BG1280 0.796 and 0.852 (the first about 110 native pixels correlate 0.81 to 0.82), BG2247 0.376 and 0.549. The PC compositions differ from the Saturn ones, and the [witnessed theatre pan of BG2247](bg2247-native-pan.md) shows the PC perspective moves the architectural landmarks. The generator prints the reason for each in the `skipped` map of `config/hd-scroll-pictures.json`.
