# IC intermission table (TP1)

One table now recognises the chapter intermission pictures that share IC0501's layout. [Patch 0185](../../patches/0185-sakura-ic-intermission-table.patch) replaces the two IC0501 constants of patch 0144 with `kIcIntermissions` (generated by `tools/gen_ic_table.py` from [`config/hd-ic-table.json`](../../config/hd-ic-table.json)) and keeps the draw path, the fades and the native fallback unchanged.

## What is specific to IC01 and what is common

| Item | IC01 (patch 0107) | IC0501 (patch 0144) and the table |
|---|---|---|
| Picture | 320 x 224 8 bpp cells, `IC01.BIN`, PC counterpart 640 x 480 | same layout for all 16 files |
| Panel and emblem | native (184,16)-(296,144) on layer 0, picture on layer 4 | identical rectangle and layers |
| Palette key | the file's own palette `530FF280499422C3` (layer 4 reports it) | the shared logo palette of `ICLOGO.BIN`, `E9107F892185CCC8`, reported by layer 4 |
| Colour offset | fitted by eye: 17/17/16 darker, from a witnessed frame | the real VDP2 offset, 0 or -16 on all channels |
| Registration | PC picture fitted to the height of the canvas, anchored 5 native pixels from the left edge, wide margins drawn | whole PC picture mapped onto the 320 x 224 viewport (rows (2y+1)*480/896, 2 x 2 samples), nothing drawn outside |
| Recogniser | palette hash, layer footprint, RGB hash `B98D70AA066A62B5` | the same checks, with the RGB hash looked up in the table |

The first witnessed IC picture (IC01) took a different route (a pause backdrop with its own palette), so nothing of its palette key, darkening or anchor generalises. IC0501 did generalise: the game paints each IC picture's cells with the **ICLOGO palette** (the palette stored in the IC file is not what is shown), the panel rectangle is fixed, and the signed offset is the native one. The disc-1 table uses that palette and rectangle when deriving candidate signatures. Each match still requires the exact displayed palette, sources and RGB.

`python tools/gen_ic_table.py build` computes, per picture: FNV-1a of the visible RGB bytes outside the panel with offset 0 and -16, the PC file size and FNV-1a (what `PcBackdropHash` checks), and a registration fit of the PC picture against the plate (the best shift over +-3 native pixels must be (0,0); all 15 pictures meet it, margin 1.2-2.4 grey levels against the best shifted fit).

The IC0501 row reproduces the in-game measurement of patch 0144 exactly (`A5E3498BEDDC1305` unshifted, `1F7A14C347473045` at -16, 218,568 bytes, `4A23AE5B5939DE76`). `build` aborts if it stops doing so, and the unit test `test_ic0501_reproduces_the_in_game_measurement` pins it. That is the evidence that the other 14 rows are the hashes the runtime will see, but it is an offline derivation, not a witness of each picture.

## Coverage

Since this work started, main gained witnessed IC03 (patch 0162) and disc-2 IC06 (patch 0183) in the same compositor. The generated table now supplies the disc-1 rows: IC0501 and IC03 reproduce their in-game hashes exactly (an independent check of the derivation), and the other 13 are offline-derived. Of those, IC06 on disc 1, IC02, IC04, IC0502, IC07-IC09 and IC1001-IC1006 (13 pictures, 13 coverage entries) have no witness and move from `paired-not-wired` to `wired-unverified`. IC01 is unchanged.

**Disc 2 is not covered.** The witnessed disc-2 IC06 shows the picture with its own palette (`FEBAEA7B6E7CAC67`) and a different RGB hash (`0F85EDA8CE4B247D`) than the ICLOGO derivation gives (`0D87B2D1DABE4DFD`), so the disc-2 pictures cannot be derived from the files alone; they need witnesses, and disc-2 rows stay `paired-not-wired`. The hand-kept disc-2 IC06 row stays in the runtime.

## Commands

```powershell
python tools/gen_ic_table.py build --iso1 "local/prepared/disc1/Track 01.iso" --iso2 "local/prepared/disc2/Track 01.iso" --pc local/work/ic-pc --map config/hd-screen-map.json --out config/hd-ic-table.json
python tools/gen_ic_table.py header config/hd-ic-table.json port/ic_intermission_table.h --check
python -m unittest tests.test_gen_ic_table tests.test_hd_chapter_coverage
```

`--pc` is any folder with `SAKURA1/ICATCH/*.SPR` extracted from the PC edition (`local/work/pc-cab/iscab.py SAKURA.mdf OUT ICATCH`). Nothing from it is committed.

## Disc 2: why it is not derivable offline (TP1 follow-up)

Compared offline, read-only, with `tools/gen_ic_table.py build`:

- All 16 `IC*.BIN` files, `ICLOGO.BIN` and `ICATALL.DAT` are **byte-identical on both discs**. The same file therefore shows different RGB on different routes, so the palette choice is not in the picture files.
- Own-palette plate of disc-2 IC06 = `0F85EDA8CE4B247D` and own palette key = `FEBAEA7B6E7CAC67`: both equal the patch 0183 in-game witness. The ICLOGO derivation gives `0D87B2D1DABE4DFD`, which was not seen.
- Disc-1 IC0501 and IC03 equal their witnesses only with the ICLOGO palette (own palette: `C997599B21F685B5`, `7240B16ECBB05835`, not seen). Disc-1 IC01 (patch 0107) is witnessed with its own palette.
- The samples exhibit both palette routes (own palette: IC01 d1 and IC06 d2; ICLOGO: IC0501 d1 and IC03 d1). Which one an appearance takes is decided by code: `LOGO.SH2` carries the IC name table and differs between discs (only 1,514 bytes, mostly relocated pointers, so no disc-specific palette table is evident). Strings in all of SAKURA1 show no other module naming ICLOGO/IC files.
- Consequence: the disc-1 IC06 row in the table (ICLOGO route) is itself unwitnessed, and the same file shows the own palette on disc 2. It stays `wired-unverified`; a disc-1 IC06 witness could be a mismatch.

`config/hd-ic-table.json` now also lists `disc2_own_palette_candidates` (own-palette `plate`, `plate_dark`, palette key per file; IC06 `reproduces-witness`, the rest `candidate-unverified`). They are not entries, not in the generated header, not wired and not counted in coverage.

**Missing datum:** per IC (at least disc-2 IC02-IC09, IC1001-IC1006, and disc-1 IC06), a layer-4 palette fingerprint (`E9107F892185CCC8` = ICLOGO route, or the file palette key in the candidates list) and the RGB hash from one real intermission, or a trace/disassembly of the SH-2 routine in `LOGO.SH2` that loads the IC file and decides whether ICLOGO.BIN is read afterwards (IC0501 doc: IC file then ICLOGO.BIN). The layer-4 palette is observable with `SATRECOMP_LAYER_PROBE` at the matching checkpoint. A runtime replay of each candidate remains pending.
